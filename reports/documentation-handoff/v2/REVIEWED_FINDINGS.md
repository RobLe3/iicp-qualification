## Windows workload-isolation assurance

**Observation.** Seven retained Windows execution packages contain environment
isolation digests reproducible from small configuration descriptors. The bound
preparation helper adds per-program firewall rules around offline preparation
checks and removes them in `finally`. The reviewed Windows process wrapper owns
process lifetime; it is not a network restriction. The macOS network sandbox is
a separate branch.

**Additional coverage.** The static follow-up mapped all 16 Windows shard
receipts, 1,344 recorded commands and 100 component/scenario selectors. An
independent reviewer reproduced those counts from the seven original archives,
matched the recorded assertions and checked 59 pinned test-source file hashes.
Some fixtures use local mocks, but file-level mock evidence is not a complete
transitive endpoint audit.

**Disposition.** A control-lifetime gap is supported within the reviewed caller
chain. Complete workload no-contact assurance remains unverified. No prohibited
contact was demonstrated, and no accepted receipt or certificate was changed.
The owning authority must assess the original requirement and any qualification
impact before proposing remediation or replay.

**Next discriminating evidence.** Trace workload-time executable/child coverage,
fixture endpoint restrictions and any independently equivalent network control;
seek original effective-state evidence where retained. Any new native control
experiment needs its own authority and both allowed-positive and denied-negative
controls. It is not part of this corpus.

## Rust provider recovery remains an investigation

[Rust SDK #183](https://github.com/RobLe3/iicp-client-rust/issues/183) describes
providers with healthy local responses but absent Directory presence and repeated
supervised exit-76 recovery. The reported release was 0.7.109. Its recovery
classification module matches the frozen candidate module byte-for-byte, but
that does not establish equivalence of the entire runtime, route or supervisor.
A completed six-case observation exercised the frozen library's actual `Node`
against a loopback fake Directory. All six controls passed: healthy heartbeats,
re-registration after a 404, route restoration without restart, exit 76 on
persistent unavailability, one fixture-managed restart after restoration, and
initial registration refusal. An independent reviewer compared 242 original Git
blobs, checked six capture hashes and did not rerun the cases.

This used 30-second heartbeats and recovery checking every heartbeat instead of
the frozen default every two. Route availability came from a synthetic runtime
handle; the full CLI, actual tunnel/route discovery and production supervisor
were not exercised. Initial refusal was tested; heartbeat credential refusal was
not. Mock registry presence is not independent real Directory persistence.
The original incident's root cause remains unresolved. The next discriminating
step is original route-discovery/tunnel/supervisor evidence or a separately
reviewed local reproduction of that boundary—not another repeat of these six
passing controls. No product correction or qualification credit follows.
Independent observation review:
`sha256:5077181d0e498ac09c2575367b890ba5b23e401bc236a973763dd60bfb3b69aa`.

[Rust SDK #175](https://github.com/RobLe3/iicp-client-rust/issues/175) concerns
experimental relay reachability. Retain that scope while examining whether
supported fail-closed fallback or safe diagnostics are affected. Do not dismiss
a supported boundary merely because one transport is experimental.
