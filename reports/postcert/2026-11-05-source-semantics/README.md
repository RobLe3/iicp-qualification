## Test names are not complete behavioral contracts

Three reviewed eligibility-before-ranking bodies exercise different fixtures:

- **Python:** regional policy leaves one EU candidate; the higher-scored US route is called zero times. The ranker input, payload and exploration receipt are checked.
- **TypeScript:** the same regional policy leaves the EU candidate and the last recorded non-discovery URL targets it. That final-URL assertion alone does not exclude earlier forbidden calls.
- **Rust:** the ranker sees two candidates rather than an unavailable third candidate; the mocks expect three failing calls to one provider and one successful call to another, with a fallback receipt. Counts alone do not establish request order. No regional policy is submitted; the unavailable candidate also lacks a confidentiality key.

The complete test files match the accepted harness revisions byte-for-byte. That establishes source-file linkage, not package equivalence or independent runtime reproduction.

## Effective-capability helper coverage

All three SDKs and both Directory implementations retain the same exact effective-capability fixture. Three SDK test files map nine matching vectors and three invalid advertisements to **36 source-assertion links**. The two Directory matching loops add **18 links** for the nine matching vectors. These are mappings, not execution counts.

All five matching helpers' test loops compare eligibility, selected variant IDs and refusal codes. The SDK loops also check the preference-unavailable flag and expected extension-identifier membership. The Directory matching loops do not assert those extra fields. A fixture being iterated is not evidence that every expected property was checked.

Four separately reviewed Directory registration/projection test bodies check selected propagated fields and rejection cases. Rust's in-memory test skips liveness checks. A separate Rust MySQL control is ignored by default and requires a disposable database; it manually seeds SQL and reads records. Its source existence proves neither that it ran nor that registration persistence was exercised. No campaign skip or waiver is inferred from this development-test annotation.

The fixture declares a pre-normative parity contract. The capability-format document separately defines scoped normative REGISTER/NODELIST clauses and opt-in Profile behavior. Preserve those distinctions; neither promote every fixture detail to a base requirement nor erase existing scoped MUST clauses.

## What the accepted records establish

Read-only use of the existing canonical validator passed **64 ledger-owned accepted receipts**, covering **5,808 command coordinates**. Six exact marker groups resolve **384 recorded package-case proofs**: 192 eligibility-before-ranking support links and 192 policy-hard-constraint links. Only the three eligibility bodies received the source-semantic assessment above; marker identity is not a complete semantic assessment of the second group.

The proofs record assertion identity, successful exit, output digest and bound package/environment context under the existing admission contract. Seven in-memory negative controls were rejected by the canonical command-proof validator. Mutated proofs were rehashed, except for the intentional digest-corruption control, so rejection was not merely an unchanged outer-hash check.

The derived trace reproduced byte-for-byte with 74 pinned input objects and three loaded canonical helpers. This is **offline reproduction of a derivative**, not re-execution of the qualification workload. Before/after source checks detect persistent drift, not an atomic guarantee against a hostile writer.

## Limits and next work

Raw-output availability, complete semantic coverage, Directory persistence execution and the final executable functional reference remain separate proof obligations. Extension membership is not deep value preservation; refusal-code equality is not full envelope validation. Passing qualification does not establish zero known defects or independent external certification.

The machine-readable source map binds retained internal review digests. Those digests do not make the controlled review records or private execution archive publicly retrievable. Public source files can be checked at the pinned commits; reproducing private receipt validation requires authorized archive access.

No qualification workload or AWS operation was performed for this analysis. Historical completeness remains false. Next work must resolve the remaining evidence and contract mappings without rewriting accepted history or treating source mappings as new credit. Publication of this supplement does not authorize a workload, deployment or release.
